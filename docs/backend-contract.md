# Jarvis chat backend contract

Same-origin endpoint `/api/chat.php?action=...`. No CORS. Fetch with `credentials: 'same-origin'`. Never render model output as HTML.

1. GET `session`: JSON `{authenticated, username, csrf, history}`. History array contains only `{role:'user'|'assistant',content}`. Anonymous is 200 with false/null/empty history; unavailable MC service is 503 for sessions carrying MC credentials. Cookie `__Host-jarvis-chat` is Secure, HttpOnly, SameSite=Strict, Path=/.
2. All POSTs require exact Origin `https://dashboard.microtechai.es` and `X-CSRF-Token: <csrf from session>`. Content-Type is `application/json` except `transcribe`, which requires browser-generated `multipart/form-data`. Obtain session before login. CSRF rotates at login/logout; use returned csrf.
3. POST `login`: `{username,password}` uses MC authentication only; JSON `{authenticated:true,username,csrf,history:[]}`. Credentials are not retained. 401 invalid credentials; 429 rate limit; 503 unavailable MC. MC token remains server-side.
4. POST `logout`: `{}` clears this chat session (not the existing dashboard login); returns anonymous session JSON and new csrf.
5. POST `message`: `{text}` only, 1–4000 Unicode characters, no client roles/history/model/URL. Authenticated each request against MC. SSE response `Content-Type: text/event-stream`: `event: delta\ndata: {"text":"..."}\n\n`, then `event: done\ndata: {"text":"complete response"}\n\n`. Terminal failure `event: error\ndata: {"error":"safe message"}\n\n`; no done follows error. Before stream starts errors use JSON `{error}` with appropriate status. Abort fetch to cancel; never retry automatically. History saved only after complete successful stream, bounded to 12 messages/18000 characters. GET session restores history.
6. POST `tts`: `{text}` only, 1–1000 Unicode characters. Authenticated/CSRF protected. Successful result binary WAV (`audio/wav`), no-cache. Chunk longer model responses in frontend. Failures JSON `{error}`. No invented audio fallback.
7. POST `clear`: `{}` clears conversation, returns authenticated session JSON. Does not reset limits.

Status codes: 400 invalid body/fields; 401 authentication; 403 Origin/CSRF; 404 action; 405 method; 413 body too large; 415 non-JSON; 429 rate or global worker busy; 502 model/TTS failure; 503 configuration/auth service unavailable. All responses no-store. SSE failures after headers retain HTTP 200 and use error event.

Limits: message 6/min/session; TTS 20/min/session; login 6/min/session (MC also enforces its own login rate). One global nonblocking flock per model and per TTS. Chat 60s, TTS 20s. Session lock released before long work. No tools or command execution from model content.

## Server setup (deployment handled separately)
Install `api/chat-config.example.php` as `/etc/jarvis-chat/config.php`, root owned 0640 group www-data. Prepare `/var/lib/jarvis-chat` owned www-data 0700 (contains sessions, locks and ephemeral TTS files). PHP requires curl, mbstring, session, proc_open. Fixed model URL defaults to `http://127.0.0.1:18010/v1/chat/completions` (private reverse tunnel); MC `http://127.0.0.1:9090`; Qwen `qwen3-coder-next`; 1024 output tokens. Piper command is argv-only `/usr/bin/taskset -c 0 /opt/jarvis-tts/venv/bin/python -m piper --model /opt/jarvis-tts/models/es_ES-davefx-medium.onnx --output_file <temp>`, OMP_NUM_THREADS=1. Fixed CPU0 affinity bounds ONNX runtime threading; CPU0 must be allowed for www-data. TTS normalizes whitespace to one input line so Piper does not overwrite the WAV per paragraph. No client selects paths or URLs. No nginx modification required; SSE buffering disabled by response header. Production requires working tunnel, MC and installed Piper model; fixture tests are not production inference/audio proof.

## Verification and remaining deployment checks
`python3 tests/chat_backend_test.py` starts isolated local PHP workers and explicitly labeled auth/model/Piper fixtures. It covers Origin/CSRF, cookie attributes, MC failure/revocation, schema limits, SSE persistence/truncation, history limits, global locks, concurrent clear, TTS argv execution, CPU affinity, timeout/cleanup, and rate limits. `tests/chat_backend_results.txt` records the real latest run. The actual Qwen design review is separately recorded at `/home/ddr/jarvis-phase3-qwen-backend.md` (HTTP 200, prompt_tokens 355, max_tokens 6000).

The suite does not prove live MC credentials, deployed nginx/FPM client-abort propagation, or real synthesized speech through this endpoint. Parent performs those production checks. TTS cannot detect a disconnected client before an output write in every SAPI, but is always bounded by its 20s deadline. Session limits are per chat cookie, not an account-wide abuse firewall; MC's own login limit and global worker locks remain in force. History is server-side PHP session data, not a durable conversation database. Do not log request bodies or TTS stdin. Server-only `JARVIS_CHAT_CONFIG` constant is used by the local test router; production directly loads `/etc/jarvis-chat/config.php`, with no request/environment config override.
